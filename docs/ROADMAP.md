# Як розвивати навичку далі

Навичка v0.1 відповідає на базові запити: одна-кілька тем × кілька мов × 2–3 роки. Нижче описано, як ітеративно розвивати її для **складніших досліджень** і **більших обсягів даних**, не втрачаючи головного: дешева модель і перевірні висновки.

## Принцип розвитку: evals-driven

Кожна ітерація проходить той самий цикл, що й під час розробки v0.1:

1. **Додати сценарії в `evals/cases.yaml`**, які описують нову здатність. Спершу вони мають **провалюватися**.
2. **Реалізувати:** детерміновану частину в коді, контекстні підказки у виводі CLI, робочий процес у `SKILL.md`.
3. **Прогнати бенчмарк** (`evals/run.py`) на Haiku та одній безкоштовній моделі й порівняти з попередньою версією (`evals/compare.py`).
4. **Реліз, лише якщо немає регресій** у детермінованих перевірках і тригерингу. У CI варто додати нічний прогін підмножини сценаріїв на Haiku з порогами.

## v0.2: надійність (найближчий крок)

| Що | Навіщо | Як |
|---|---|---|
| Обов'язкова перевірка відповіді в чаті | Бенчмарк: 3 з 21 прогонів містили похідні або вигадані числа («на 31 п.п.», «довіра 85») | Команда `wir answer <id> --file` перевіряє відповідь і повертає її з позначками; hook у Claude Code (`Stop`) або крок у harness |

| Паралельні запити в межах лімітів | Холодний старт 5 мов ~10 с; для 20+ мов довго | Пул з 4–8 з'єднань, спільний rate limiter з урахуванням `Retry-After` |
| Кращі тригери для «продовж дослідження X» | 1 з 3 прогонів не вмикає навичку | Розширити опис; `study list` у підказках; trigger-evals з такими запитами |
| Більше мов звіту | Зараз uk/en | Рядки в `src/wir/data/report_i18n.json`; шрифти Noto для CJK / арабської з RTL |

## v0.3: складніші дослідження

- **Тема як граф понять.**
  - Автоматично пропонувати пов'язані поняття через властивості Wikidata: підкласи (P279), частина чогось (P361), «facet of» (P1269).
  - Або брати статті з категорії.
  - Агент підтверджує кластер, а код рахує «широту»: чи рухаються статті разом. Правила `narrow_breadth` і `dominant_article` уже є.
- **Портфель тем.** Порівняння 10–50 тем в одній мові («яку тему курсу запускати наступною») з рейтингом і групуванням.
- **Пошук, де тема росте найшвидше.** Сканування всіх ~350 мовних розділів з sitelinks поняття, рейтинг за відносною зміною. Це природне продовження прикладу 3.
- **Додаткові сигнали довіри:**
  - `edits/per-page`: сплеск переглядів разом зі сплеском редагувань підтверджує реальну подію;
  - `top-per-country`: інтерес по країнах, а не лише по мовах (з урахуванням прихованих країн);
  - зовнішні сигнали на кшталт Google Trends як незалежна перевірка, якщо користувач дасть доступ.
- **Прогноз з інтервалом.** ETS або сезонна модель на 6–12 місяців з інтервалом невизначеності. Лише для рядів з довірою High, щоб не продавати шум як прогноз.
- **Пояснення сплесків.** Зіставлення разових місяців із подіями: заголовні статті, новини на головній сторінці Вікіпедії («Current events» / «In the news»).

## v0.4: великі обсяги даних

REST API розрахований на точкові запити. Орієнтовно це 3 запити на статтю-рік і серію, тобто на 10 000 статей × 50 мов × 3 роки — **мільйони запитів**. Це неприйнятно ні для Wikimedia, ні за часом. Шлях масштабування:

1. **Дампи замість API.** Wikimedia публікує повні добові дампи переглядів ([dumps.wikimedia.org/other/pageview_complete](https://dumps.wikimedia.org/other/pageview_complete/)). Один завантажений файл містить усі статті всіх розділів за день.
2. **Локальне аналітичне сховище.** Добові дампи перетворюються на Parquet, розбитий за мовою й місяцем, а запити йдуть через DuckDB. Агрегати «стаття × місяць» займають набагато менше за сирі дані, і сканування сотень тисяч статей стає питанням секунд.
3. **Інкрементне оновлення.** Щоночі дочитується один новий день; завершені місяці незмінні, як і зараз у кеші.
4. **Той самий інтерфейс для агента.** `study new` сам обирає джерело: API для малих досліджень, сховище для великих. Агент і `SKILL.md` не змінюються, змінюється лише шар даних (`collect.py`).
5. **Зведення для моделі.** При 500 статтях у контекст потрапляє лише топ і розподіли, а таблиці йдуть у CSV/Parquet і PDF. Той самий принцип «сирі дані у файлах», що й зараз.

## v0.5: продукт

- **MCP-сервер** поверх тих самих модулів, щоб підключати навичку до будь-яких клієнтів MCP.
- **Моніторинг.** Збережене дослідження перераховується за розкладом і сповіщає, коли висновок або довіра змінилися. `changes_since_previous_state` уже є.
- **Інтерактивний HTML-дашборд** поруч із PDF. Для команди зручно, коли його можна відкрити й покрутити самому.
- **Спільні дослідження** для команди: `wiki-studies` у репозиторії або спільному сховищі, історія змін як журнал рішень.

## Чого свідомо не робити

- **Не замінювати правила довіри «чорною скринькою».** Засновнику потрібне пояснення, а не бал.
- **Не давати моделі рахувати.** Навіть різниця двох чисел, яку модель порахувала сама, у бенчмарку виявилася джерелом помилок.
- **Не робити висновків про попит.** Навичка каже, що перевіряти далі, і завжди називає межі даних.
