# План тестування навички `wikipedia-interest-research`

> Документ описує, **що** ми перевіряємо, **як** і **за яким критерієм** вважаємо результат прийнятним.
> Тестуємо не лише код, а й поведінку агента на дешевій моделі. Саме тут навички найчастіше ламаються.

## 1. Цілі

1. **Коректність даних.** Числа, які рахує навичка, збігаються з першоджерелом (Wikimedia) і з офіційним інструментом Pageviews Analysis.
2. **Коректність висновків.** Метрики та індекс довіри правильно розпізнають справжній ріст, сезонність, разові сплески, ботів і загальні зміни трафіку розділу.
3. **Надійність агента на дешевій моделі.** Haiku 4.5 і безкоштовні моделі OpenRouter:
   - вмикають навичку, коли треба;
   - виконують повний сценарій;
   - не вигадують чисел;
   - чесно називають обмеження.
4. **Ефективність.** Мінімум викликів інструментів і токенів. Повторні та уточнювальні запити мають бути дешевшими за перший.
5. **Корисність результату.** Людина без технічного бекграунду за хвилину розуміє висновок і може переслати PDF.

## 2. Що не тестуємо (свідомі межі)

- Бізнесову правильність рекомендацій. Інтерес до статті ≠ готовність платити. Навичка лише пропонує напрям для подальшої перевірки і прямо про це пише.
- Роботу Wikimedia API як сервісу, зокрема його аптайм. Тестуємо лише нашу реакцію на його помилки.

## 3. Рівні тестування

| # | Рівень | Що перевіряємо | Інструмент | Де запускається |
|---|---|---|---|---|
| 1 | **Unit** | Метрики, індекс довіри, заповнення пропущених днів, відкидання неповних місяців, нормалізація | pytest на **синтетичних рядах із відомою відповіддю** | CI |
| 2 | **Контракт API** | Парсинг відповідей, 404, 429 + `Retry-After`, URL-кодування (кирилиця, діакритики, `/`), редиректи, мапінг через Wikidata | pytest + записані фікстури; `@live` smoke-тести | CI (фікстури), вручну (live) |
| 3 | **CLI** | JSON-схема виводу, розмір резюме дослідження ≤ 1 000 + 800 × кількість комірок (мова × тема) символів, коди виходу, зрозумілі повідомлення про помилки, `--help` | pytest + subprocess | CI |

| 6 | **Коректність даних** | Наші числа = числа з [pageviews.wmcloud.org](https://pageviews.wmcloud.org) | Ручна звірка 3 кейсів + скріншоти в `docs/` | Крок 3 |

| 9 | **Людське рев'ю** | Якість звіту за рубрикою (розділ 8) | Чекліст | Кроки 7, 10 |

### 3.1. Синтетичні ряди для unit-тестів (рівень 1)

Модель ряду фіксуємо заздалегідь, тож правильна відповідь відома:

| Ряд | Очікуваний висновок |
|---|---|
| Стабільний лінійний ріст +3%/міс, шум ±5% | Ріст, довіра **High** |
| Сезонність (пік щовересня), без тренду | «Стабільно, сезонність». Вересневий пік **не** вважається ростом |
| Рівний ряд + один сплеск ×20 за 3 дні | Без сплеску росту немає → довіра **Low**, причина «разовий сплеск» |
| Ріст лише в desktop, стрибкоподібний | Попередження «ботоподібний трафік» |
| Стаття росте так само, як увесь розділ | Відносна частка незмінна → ріст **не** приписується темі |
| < 100 переглядів/міс | Довіра **Low**, причина «замало даних» |
| Історія 10 місяців | Немає порівняння рік до року → попередження, довіра ≤ Medium |
| Пропущені дні (0 переглядів) | Заповнюються нулями, а не інтерполюються |
| Monthly-запит з кінцем у поточному місяці | Неповний місяць відкидається |

## 4. Середовища для агентних тестів

Claude Code у користувача має 50+ навичок і MCP-конектори. Вони конкурують з нашою навичкою за увагу моделі. Тому перевіряємо в трьох середовищах:

| Середовище | Як запускається | Що бачить модель | Навіщо |
|---|---|---|---|
| **baseline** | Порожня тека, `--setting-sources project --strict-mcp-config` | Стандартний Claude Code (13 вбудованих навичок), **без нашої** | Точка відліку: що модель робить сама |
| **clean** | Пісочниця з `.claude/skills/wikipedia-interest-research`, ті самі прапорці | Стандартний Claude Code + наша навичка | Якість самої навички |
| **realistic** | Пісочниця без прапорців | Усі навички й MCP-конектори користувача | Чи обирає модель нашу навичку серед конкурентів |

Для безкоштовних моделей OpenRouter використовуємо власний міні-агент (`dev/harness/`). Він має режими «з навичкою» та «без».

**Моделі:**
- Claude Haiku 4.5 — основна ціль;
- 2–3 безкоштовні моделі OpenRouter з підтримкою tool calling (обираємо на кроці 8 за актуальним списком `/api/v1/models`);
- для порівняння: 1 прогін на сильнішій моделі (Sonnet), щоб показати, що навичка не «зламана» для потужних моделей.

## 5. E2E-сценарії

Повний формат із перевірками лежить у [`evals/cases.yaml`](../evals/cases.yaml). Коротко:

| ID | Сценарій | Що саме перевіряє |
|---|---|---|
| `fasting-pl-cs` | Приклад 1: інтервальне голодування, PL проти CS, 2 роки | Мапінг назв між мовами, порівняння, нормалізація на розмір розділу |
| `astronomy-uk-trust` | Приклад 2: астрономія в UK, чи росте і чи можна довіряти | Індекс довіри; сезонність (вересневі піки) не приймається за ріст |
| `english-learning-report` | Приклад 3: вивчення англійської в обраних мовах + звіт | Ранжування аудиторій, PDF, рекомендації «що дослідити далі» |
| `english-learning-no-langs` | Приклад 3 без переліку мов | Агент уточнює мови або явно називає своє припущення |
| `followup-add-lang` | Кілька ходів: «додай словацьку» → «візьми 3 роки» | `study update`, без повторного завантаження, історія припущень |
| `ambiguous-topic` | «Меркурій» | Уточнення або явний вибір значення (планета / елемент / бог) |
| `missing-article` | Тема, якої немає в одній з мов | Чесно показує відсутність і нічого не вигадує |
| `low-volume-language` | Мала мова / мало переглядів | Довіра Low з поясненням |
| `news-spike` | Тема з новинним піком | Сплеск не видається за тренд |
| `custom-weights` | «Для нас важливіший ріст, ніж розмір аудиторії» | Зміна ваг, перерахунок рейтингу |
| `english-query` | Запит англійською | Відповідь і звіт англійською |
| `resume-session` | Нова сесія: «продовж дослідження …» | `study show`, контекст без перерахунку |
| `offline-cache` | Мережа недоступна, дані є в кеші | Працює з кешу або пояснює, чого бракує |
| `negative-unrelated` | Запит не про інтерес / Wikipedia | Навичка **не** вмикається |

## 6. Перевірки (assertions)

**Детерміновані** (скрипт перевіряє транскрипт і файли):

| Перевірка | Як |
|---|---|
| `skill_triggered` | У транскрипті є активація навички / читання `SKILL.md` |
| `used_cli` | Дані отримано через `scripts/wir`, а не через власні скрипти чи WebFetch |
| `artifacts_exist` | Є `report.pdf`, `summary.md`, CSV, PNG |
| `pdf_one_page` | PDF має рівно 1 сторінку |
| `numbers_match_study` | **Кожне число з відповіді в чаті збігається з `study.json` (допуск ±1% або округлення)** |
| `no_invented_titles` | Кожна згадана стаття чи мова є в `study.json` |
| `mentions_trust` | У відповіді є рівень довіри (High/Medium/Low або переклад) |
| `mentions_limitations` | Є розділ про припущення та обмеження |
| `answer_language` | Мова відповіді = мова запиту |
| `max_tool_calls` | Кількість викликів інструментів ≤ ліміту сценарію |
| `followup_is_incremental` | На уточнення викликано `study update`, мережевих запитів менше, ніж на першому ході |

**LLM-суддя** (Sonnet за рубрикою, оцінка 1–5 з обґрунтуванням):
- висновок відповідає на поставлене питання;
- рекомендація спирається на дані, а не на загальні знання моделі;
- обмеження названо конкретно (наприклад «мова ≠ країна», «інтерес ≠ готовність платити», сезонність);
- текст зрозумілий засновнику без аналітичного бекграунду.

## 7. Метрики та критерії приймання

Для кожної пари «середовище × модель» рахуємо:
- **pass rate** (частку пройдених перевірок; середнє ± std за 3 прогони);
- медіанну кількість викликів інструментів;
- токени (input/output);
- час;
- вартість.

| Критерій | Поріг |
|---|---|
| Unit + контракт + CLI + звіт | 100% зелені в CI |
| Haiku, **clean**, детерміновані перевірки | ≥ 90% |
| Haiku, **realistic**, `skill_triggered` на позитивних запитах | ≥ 80% |
| Тригеринг: хибні спрацювання на негативних запитах | ≤ 10% |
| `numbers_match_study` | **100%** (вигадані числа неприйнятні) |
| Безкоштовні моделі, clean | ≥ 70% (орієнтир: вони слабші в tool calling) |
| Уточнювальний хід дешевший за перший за токенами | так |
| Приріст pass rate з навичкою проти baseline | суттєвий і показаний у таблиці |

## 8. Людське рев'ю звіту (рубрика)

Для кожного з 3 прикладів із завдання відповідаємо так/ні:

- [ ] Висновок видно одразу, в одному реченні вгорі.
- [ ] Графік читається без пояснень: підписані осі, мови й періоди.
- [ ] Є рейтинг з рівнем довіри для кожної мови.
- [ ] Пояснено, **чому** довіра саме така.
- [ ] Є конкретна рекомендація «що дослідити далі».
- [ ] Є блок «Припущення та обмеження».
- [ ] Вказано джерело, дату вибірки та параметри (agent=user, період).
- [ ] Усе вміщується на 1 сторінку A4 і не виглядає перевантаженим.
- [ ] Звірка з pageviews.wmcloud.org для однієї мови збігається.

## 9. Ризики тестування та як їх знімаємо

| Ризик | Рішення |
|---|---|
| Недетермінованість LLM | 3 прогони на сценарій, середнє ± std |
| Дані Wikipedia оновлюються щодня | Еталоном для перевірки чисел служить `study.json` конкретного прогону, а не зафіксовані числа |
| Ліміти безкоштовних моделей (≈20 запитів/хв, 50–1000/день) | Невеликий набір сценаріїв для free-моделей, паузи, збереження проміжних результатів |
| Агентні прогони мають доступ до shell | Кожен прогін в окремій тимчасовій теці; перелік дозволених інструментів обмежено |
| Тест перевіряє не те | Спершу запускаємо baseline: перевірки мають **провалюватися** без навички й проходити з нею. Перевірки, що проходять завжди, прибираємо |
